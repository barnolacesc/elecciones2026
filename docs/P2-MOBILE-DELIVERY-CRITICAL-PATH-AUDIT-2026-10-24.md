## Reproducible observations

- `render_base` emits one blocking `styles.css` link (`src/elecciones2026/generator.py`, near line 1048). The first two lines of that stylesheet import `tokens/tokens.css` and `themes.css`. Thus the imported CSS cannot be requested from parsing the HTML alone; it is discovered only after `styles.css` arrives. Both imports can then be fetched in parallel. This is one additional dependency tier, not evidence of a measured delay.
- `render_home_page` emits deferred `sharing.js`, an optional `budget-context.js`, a content-hashed comparison bundle, and `app.js` in that order (generator, near lines 1405–1408). The comparison bundle varies by build and is not sized by the source-file figures below. The generated HTML, third-party source navigation, and mobile browser timings are not measured here.
- Source-file sizes at this commit, generated by Node 24 `zlib.gzipSync(...,{level:9})`; the compressed figures are *potential* per-file payload sizes, not observed Nginx/edge transfer bytes:

  | Source file | Raw bytes | gzip-9 bytes |
  |---|---:|---:|
  | `site/styles.css` | 35,600 | 5,125 |
  | `site/tokens/tokens.css` | 4,210 | 1,510 |
  | `site/themes.css` | 37,679 | 7,229 |
  | `site/app.js` | 68,675 | 14,489 |
  | `site/sharing.js` | 4,436 | 1,540 |

  The three CSS sources total 13,864 gzip-9 bytes; app and sharing source total 16,029. These are not a page-weight total: they exclude HTML, comparison data, optional budget code, headers, and images. Nginx enables gzip for CSS and JavaScript at level 6, so these level-9 figures must not be presented as actual response sizes.
- `nginx/default.conf` gives every `.css` and `.js` asset a one-year `immutable` cache lifetime, although `styles.css`, `themes.css`, `app.js`, and `sharing.js` have stable filenames. A returning reader can therefore use old interface code or styles after a deployment until cache invalidation or URL versioning occurs. This is a cache-consistency risk, not proof of a currently stale user session. It is particularly relevant while mobile/share fixes are being reviewed in #125, #128 and #134. Do not change that cache contract here while those branches and the release pipeline are active.
- The prior `docs/QUIZ-PERFORMANCE.md` records synthetic quiz cold-readiness p95 633.3/595.2/609.8 ms at 360/390/430 px, above its *proposed* 500-ms target. That is a different mock quiz artifact and cannot stand in for comparator timing. Existing E2.5 notes record only three historical cold local HTTP samples (FCP 680–740 ms; DOMContentLoaded 778–789 ms), not current production or 2023 pilot acceptance.

## Next bounded engineering decisions

1. After the overlapping P2 PRs settle, measure the **generated** private 2023 artifact at 360/390/430 px: cold and warm cache, simulated 1.6-Mbit/s/150-ms network, and fourfold CPU slowdown. Capture navigation/FCP, first usable compare/share controls, response sizes, and resource initiators. Record five runs per condition and report raw samples plus p95; test deep-link entry and back/forward restoration separately. Repeat on physical iOS Safari and Android Chrome before E2.5 sign-off. No personal political answers or PDFs belong in the trace.
2. Compare a candidate that removes the CSS import dependency tier (for example, safely bundled or preloaded styles) against the exact baseline artifact. Retain visual, 320/360/390/430-px overflow, focus, touch-target and reduced-motion checks; accept only a measured improvement without regression. Do not infer a speed-up from source bytes alone.
3. Resolve stable-name `immutable` assets by either content-addressed URLs across the complete generator/HTML/serving path or a revalidated/short-lived policy for unversioned assets. Test an A→B→A private preview and cache behavior before release. Do not weaken content-addressed bundle caching or call a CDN purge a durable fix.
